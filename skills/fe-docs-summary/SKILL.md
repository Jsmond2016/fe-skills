# 问题解决过程总结

用户使用 AI 完成需求、任务或解决 BUG 后，调用本技能自动生成结构化汇总文档，记录"遇到了什么问题 → 经历了什么过程 → 最后怎么解决的"全链路，方便日后复盘。

## 触发场景

当用户明确表达「使用该 skill 做总结」、「记录一下解决过程」、「生成解决文档」等意图时，结合当前对话上下文（已解决的问题/需求/BUG），生成总结文档。

**不触发**：用户仅提出新需求、提问或闲聊，未涉及已完成的问题解决过程。

## 文档存放路径规范

文档统一存放在项目根目录的 `docs/` 目录下，根据内容性质决定存放位置：

### 路径规则

```
# 若与业务模块相关（推荐）
docs/{业务名}/{yyyyMMdd}-{文档标题}.md

# 若无明确业务归属（默认兜底）
docs/{yyyyMMdd}-{文档标题}.md
```

### 示例

| 场景 | 文档路径 |
|:-----|:---------|
| 用户模块增删改查 | `docs/用户系统模块/20260701-用户模块增删改查需求.md` |
| 订单列表性能优化 | `docs/订单系统/20260701-订单列表性能优化.md` |
| 修复登录状态丢失 | `docs/登录模块/20260701-登录状态丢失修复记录.md` |
| 通用工具函数封装 | `docs/20260701-通用日期格式化工具函数封装.md` |

### 目录处理

- 如果 `docs/{业务名}/` 目录不存在，先创建目录再写入文件
- 如果 `docs/{业务名}/` 目录已存在，直接写入
- 如果项目没有 `docs/` 目录，先在项目根目录创建

## 文档命名规范

```
{yyyyMMdd}-{文档标题}.md
```

- **前缀**：当前日期，格式 `yyyyMMdd`（如 `20260701`）
- **连接符**：英文连字符 `-`
- **文档标题**：概括问题/需求的核心内容，使用中文；文件层级目录（如果有）的命名风格应与之一致
- **文件扩展名**：`.md`

## 文档元信息

每份文档开头需补充元信息块，包含时间、标签、使用模型、总耗时等字段：

```markdown
# {文档标题}

> **编写时间**：{yyyy-MM-dd HH:mm}
> **使用模型**：{模型名称（如 Claude Sonnet 4.6）}
> **标签**：{标签1, 标签2, 标签3}
> **总耗时**：{约 XX 分钟}

---
```

### 各字段说明

| 字段 | 说明 | 获取方式 |
|:-----|:------|:---------|
| `编写时间` | 文档创建时间 | `date +%Y-%m-%d` 格式，取当前日期 |
| `使用模型` | 本次使用的 AI 模型 | 使用当前 AI 模型的名称（如 Claude Sonnet 4.6） |
| `标签` | 便于检索的关键词 | 根据内容提炼 3-5 个标签，如 `用户模块, CRUD, 表单校验` |
| `总耗时` | 本次解决问题的大致耗时 | 根据对话时间跨度估算，格式如"约 30 分钟" |

## 文档内容结构

文档正文采用三段式结构：**背景与问题 → 解决过程 → 最终方案**。

### 1. 背景与问题

描述本次要解决的问题或需求，包含：

- **需求/问题描述**：清晰说明遇到了什么问题或需要实现什么功能
- **原有现状**（可选）：说明改动前的状态
- **预期目标**：期望达到的效果

### 2. 解决过程

记录解决过程中的关键节点，包含：

- **思路分析**：分析问题的根因或设计方案时的思路
- **关键步骤**（推荐使用编号列表）：
  1. 步骤一：做了什么
  2. 步骤二：做了什么
  3. 步骤三：做了什么
- **遇到的坑**（可选）：过程中遇到的意外问题或注意事项
- **方案对比**（可选）：如果有多方案对比，记录权衡过程

### 3. 最终方案

总结最终的落地交付成果，包含：

- **核心变更**（推荐使用列表）：改了什么、新增/修改/删除了哪些内容
- **关键代码/配置**（可选）：贴出核心代码片段
- **效果验证**：如何验证方案有效（测试用例、手动验证、截图等）

## 完整文档示例

```markdown
# 用户模块增删改查需求

> **编写时间**：2026-07-01 14:30
> **使用模型**：Claude Sonnet 4.6
> **标签**：用户模块, CRUD, 表单校验, 权限控制
> **总耗时**：约 45 分钟

---

## 背景与问题

### 需求描述
实现后台管理系统的用户模块基础功能，包括用户的增删改查操作。

### 原有现状
系统没有任何用户管理功能，用户数据需直接通过数据库操作。

### 预期目标
- 提供可视化的用户管理页面
- 支持用户的增删改查操作
- 表单包含必要的校验规则
- 仅管理员可操作用户管理

## 解决过程

### 思路分析
采用前后端分离方式，前端使用 Ant Design Pro 的 ProTable 和 ProForm 快速搭建，后端已有统一的 CRUD 接口规范，只需新增用户相关接口。

### 关键步骤

1. **设计数据库模型**：定义 User 表结构，包含用户名、邮箱、角色等字段
2. **后端接口开发**：新增用户 CRUD 接口，遵循现有 RESTful 规范
3. **前端页面开发**：使用 ProTable 实现用户列表，ProForm 实现新增/编辑表单
4. **表单校验**：添加邮箱格式、用户名长度、密码强度等校验规则
5. **权限集成**：接入现有权限中间件，仅管理员可访问用户管理页面

### 遇到的坑

- **邮箱唯一性校验**：后端未校验邮箱唯一性，导致可创建重复邮箱用户；修复后添加了唯一索引 + 后端校验
- **删除确认**：未做二次确认，误删后无法恢复；增加了 Popconfirm 确认弹窗

## 最终方案

### 核心变更

- **新增** `src/pages/User/` — 用户管理页面（列表、新增、编辑、删除）
- **新增** `src/services/user.ts` — 用户模块 API 封装
- **新增** `server/src/routes/user.ts` — 后端用户 CRUD 接口
- **修改** `server/src/prisma/schema.prisma` — 新增 User 模型定义

### 关键代码

**后端 User 模型**：
```prisma
model User {
  id        Int      @id @default(autoincrement())
  username  String   @unique
  email     String   @unique
  role      Role     @default(USER)
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
}
```

**前端校验规则**：
```typescript
const rules = {
  username: [{ required: true, message: '请输入用户名' }, { min: 2, max: 20 }],
  email: [{ required: true, type: 'email', message: '请输入有效邮箱' }],
  password: [{ required: true, min: 6, message: '密码至少 6 位' }],
};
```

### 效果验证

- 新增/编辑/删除用户功能正常
- 表单校验生效（空值、格式错误均有提示）
- 非管理员访问用户管理页面返回 403
- 存在重复邮箱时返回"邮箱已被注册"错误提示
```
